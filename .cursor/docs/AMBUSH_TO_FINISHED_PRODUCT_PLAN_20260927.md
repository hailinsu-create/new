# Ambush Loop 从 R44 到成品：开发总计划

日期：2026-09-27
状态：M0 执行中；基线、隔离冒烟和首次 APK 已完成，见 `AMBUSH_M0_BASELINE_20260927.md`；真机修复包与陌生人首局待闭环。
远端基线：cursor/ambush-play-r44-0641，c87aee4b587954e4102e1c77758178b0f79a17ad，PR #64，Draft，5 个提交。
成品目标：安卓横屏、中文、离线单机、六夜完整战役；先完成可独立交付的 1.0 侧载正式包，商店发行作为后续 S 阶段。

## 1. 这次“做到成品”的定义

玩家从下载、安装、首次教学，到六夜通关、查看战役档案、退出后继续，均不需要开发者陪同、键盘或参考通关脚本。游戏拥有一致的视觉与声音、可理解的失败反馈、可靠存档、可升级安装包和可追溯构建。

1.0 保留现有核心乐趣：侦察 → 搜刮 → 组队布置 → 拉响警报 → 自动伏击 → 打扫与下一波 → 撤离；失败后根据情报修改计划。
六夜固定为院子、仓道、泵站、信号楼、油库、电台。先提高每夜的辨识度与决策质量，不用增加关卡数量证明成品程度。

目标参考仍是 Commandos 2 的夜袭氛围与小队可读性；沿用原创风格化多边形角色、脚本生成场景道具与合成音。是否成品以实际体验和验收判断，不以必须换成 sprite、加入配音或主观“9.5 分”为条件。

1.0 明确交付：

- 六夜完整流程、清晰教学、失败复盘、可靠重试与通关收尾。
- 全触控操作、返回键与后台恢复、安全区适配、标准/省电档。
- 稳定保存进度、设置，以及明确承诺的安全边界计划和失败情报。
- Release 签名 APK、SHA-256、版本说明、安装/升级/数据说明、已知问题。
- 对应源码标签、构建说明、自动化/截图/试听/试玩/真机证据。

本期排除：第 7 夜及 12 关扩张、FOW、联网、账号、广告/内购、局外数值成长、车辆/多层场景、新人物面部管线、全面改写战斗模拟。桌面导出可用于验证，独立桌面商业发行另立范围。Play AAB 和商店上线见第 11 节。

## 3. 阶段路线与预算

工作量是规划估算，不是服务时长承诺。假设一名负责集成的开发者配合 AI、六夜范围不扩大、能获得测试设备与试玩者。每阶段按验收退出，不因耗尽预算自动判定完成。

| 阶段 | 主要交付 | 依赖 | 估算净工作日 |
| --- | --- | --- | --- |
| M0：可复现且安全的开发基线 | 远端一致工作副本、隔离测试入口、当前版本冒烟、可安装开发 APK | 无 | 2–4 |
| M1：完成 R45–R53 | 九个独立玩法反馈切片、回归与触控画面、0.6.37/code 86 | M0 | 3–5 |
| M2：院子达到成品首局 | 首局教学、失败→改计划闭环、安全续玩契约、首次盲测 | M1；M0 先做一次诊断性试玩 | 4–6 |
| M3：六夜统一品质 | 全战役节奏、非参考方案检查、美术/动画/混音修整、全战役盲测 | M2 | 6–10 |
| M4：安卓可靠性封板 | 存档与升级、设备性能、系统交互、回归自动化、Beta 候选 | M3；平台问题从 M0 提前处理 | 5–8 |
| M5：候选版到 1.0 | 同一候选版本证据包、Release APK、源码标签、发行说明、恢复方案 | M4 | 3–5 |

净工作量合计 23–38 天；预留约 25% 修复与复验预算后约 29–48 天。按连续投入折合约 6–10 个工作周；设备到位、真人招募、外部审核的等待时间另计。M0 完成后，根据真实编译、冒烟、安装和首局结果重新估算一次。

主要依赖顺序：M0 → M1 → M2 → M3 → M4 → M5。首次 APK、真人诊断、签名调查前置；正式全量证据在候选版收敛。独立工作可以穿插，但同一时刻 main.gd 和 smoke_test.gd 各只有一个修改者。本计划不启动额外代理或定时任务。

## 4. M0：先让开发和验证可复现

### M0-01 分支、版本与构建身份

- 核对远端分支当前 SHA，准备与之相同的干净工作副本；保留上轮本地提交和本轮规划文档。
- 记录工程、导出预设、包名、versionName/versionCode、Godot/模板/JDK/SDK 版本与路径。
- 清点主线与旧 Codex 的能力差异：每项标记“主线已覆盖 / 待适配 / 历史废弃”，附代码入口和验证方法。
- 首先审计：存储隔离、原子存档、安全区坐标、触摸取消/多指、后台暂停、1×/2×一致性。迁移可验证的能力和用例，不复制旧三关主场景。

交付：基线清单、差异表、可重复执行的环境检查入口。

### M0-02 修复测试存储隔离

- 在 Godot 启动、Autoload 初始化之前建立唯一测试数据空间；可采用经验证的独立 OS 用户数据目录，或统一可注入存储路径。
- 覆盖进度、设置、教学标志、情报及所有截图/导出探针写档路径；仅修改 main 场景里的路径不够。
- 测试入口必须检查路径属于本次测试目录；缺失隔离参数时立即失败，不能回退到玩家默认路径。
- 所有清理只能针对已验证的本次测试目录。
- 在受控沙箱中建立“模拟玩家档”哨兵，验证正常结束、断言失败、强制终止都不改变其字节；对真实玩家文件只做只读哈希检查，不人为覆盖。
- 备份再恢复玩家档不算隔离；异常退出可能跳过恢复。

退出条件：隔离守卫的正反测试通过，Autoload 和场景使用同一隔离空间。此门未过，不执行现有 _wipe_save 冒烟。

### M0-03 基线运行与第一台手机

- 安装或定位 Godot 4.7.2 标准版、匹配模板及 Android 工具链。JDK/SDK 依照版本化的 [Godot 4.7 Android 导出说明](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_android.html)核实；不要照抄过时本机路径。
- 完成资源导入后，通过已验证的隔离入口运行主冒烟。要求退出码 0，并出现 SMOKE_SLICE_COMPLETE 与 SMOKE_OK_RAID_LOOP；其他模块标记按当前源码核验。
- 启动标题→进入院子，记录基线截图和一段实际输入录像。
- 导出开发 APK，优先在一台可用 arm64 手机完成安装、冷启动、触控警报、失败或胜利后继续、返回键与后台恢复。
- 在当前已验证包上安排 1 名陌生人的诊断性首局，记录真实卡点，作为 M1/M2 排序依据。
- 保存引擎版本、命令、源码 SHA、APK 哈希、设备信息和结果。

M0 退出：测试不碰玩家档；当前源码可导入且冒烟通过；至少一台手机成功安装并完成最小输入闭环。无设备时可继续不依赖设备的任务，但 M0 真机项保持未完成，后续不能冒称安卓已通过。

## 6. M2：院子成为成品样板

本阶段优先解决陌生人真实卡点。已存在的功能先复验，问题复现后修改。

### M2-01 首局教学和反馈

目标动作链：选人 → 走近匣 → 理解开匣进度 → 拿枪 → 跟随/布置 → 看懂射界 → 拉警报 → 打扫 → 下一波/撤离。

- 一次只显示当前阶段需要的一条主要教学；手机优先显示触控语言。
- 教学可重看，正常关闭后不会反复遮挡操作；新档、老档和中途退出行为明确。
- 按钮区分可用、不可用原因和操作完成；近邻世界热区有稳定点击优先级。
- 失败牌引用真实漏网/阵亡/资源事件；事实与建议分开，建议写“下次可尝试”。
- 至少验证三种非参考失败：朝向错误、关键入口无人覆盖、资源/工具使用不当。不能只测试参考站位。
- 复盘、暂停、倍速、跳到终局的现有入口逐项检查，避免为同一需求再加按钮。

### M2-02 确定并实现续玩契约

正式包最低承诺：

- 保存已解锁/通关关卡、教学状态、音频/画质设置。
- 在安全边界保存当前关卡的上次有效准备方案与有限失败情报，按关卡 ID 隔离。
- 退出或系统结束进程后，从最近已提交的安全边界恢复；不承诺逐帧恢复正在进行的枪战。
- 第一次进入 ALERT 前、失败/通关结果落定后等边界何时写档必须形成明确表格。
- 提示玩家实际恢复位置，不能悄悄把“继续进度”变成无情报的新局。

采用版本化数据与稳定 ID；迁移旧 cfg 时保留已有进度和设置。引入原子写入与保存失败反馈。未来 schema 不受支持时保留原档、明确提示，不自动覆写成新档。实施可复用旧 Codex 思路，但必须适配六夜、当前 RAID 状态和 GameSettings 的写入入口。

### M2-03 样板盲测

在尽可能接近候选版本的手机上观察至少 5 名未参与开发的玩家。主持人不提供通关方案；救援提示要记录。

建议退出目标（制定的目标，不是已有结果）：

- 至少 4/5 在 3 分钟内完成首次有效警报。
- 至少 4/5 在经历失败后，能指出一项有证据的原因并实际修改计划。
- 每名玩家均能找到重试/继续；没有必须求助才能离开的界面。
- 同一阻塞性误解若出现在 2 人及以上，列为本阶段必须修复。
- 收集完整尝试次数、等待时间、误触、求助点和主观继续意愿；不能只记录成功者。

修复后尽量使用新玩家复测；样本较小，只用来发现问题，不宣称统计代表全部用户。

M2 退出：院子可独立上手；失败→修改→重试顺畅；续玩契约通过退出重启验证；样板美术/触控层级已确定，可向其余五夜推广。

## 7. M3：六夜内容、画面与声音统一

### M3-01 六夜的体验职责

以下是对已有机制的整理方向，不代表新增系统。

| 夜次 | 玩家应掌握的决策 | 完成证据 |
| --- | --- | --- |
| 院子 yard | 搜刮、组火力、交叉覆盖、波间行动 | 陌生人能独立完成基础闭环 |
| 仓道 warehouse | 弹药与入伏时机，读懂黄区 | 玩家知道何时开火，并能解释一次过早/过晚的后果 |
| 泵站 pump | 门状态与作者备用路线的关系 | 改门前后路线可读，相关方案确实有效 |
| 信号楼 railcut | 双通道与延迟侧翼覆盖 | 入口和延迟提示明确，不靠背攻略补第二方向 |
| 油库 depot | 多入口分工、西路与绊索 | 油罐地标、入口分布和关键布置一眼可区分 |
| 电台 radio | 暗道与回波节奏、全战役综合运用 | 从简报到战斗能理解延迟威胁，终局具有收尾感 |

每夜登记：新增或复用决策、参考通关、至少一种非参考尝试、典型失败和针对性建议、耗时、卡点。
无需强求所有任意站位都能赢；检验替代方案及工具价值，避免“唯一隐藏脚本解”。

至少 3 名玩家完整走完六夜；观察每夜是否出现重复劳动、提示过载和不透明失败。先测实际首通时间，再设宣传口径，不按关卡数量推算“45–90 分钟”。

保留既定作者路线和数值约束；如果人测暴露真正的平衡问题，单开玩法变更切片，说明前后行为并重建相关基准，不与视觉修整混提交。

### M3-02 美术、动画与 UI

- 院子样板的配色、字阶、热区、遮挡处理统一到六夜。
- 玩家缩放下可辨敌我、三名队员、方向和主要道具；危险不能只靠颜色表达。
- 优先修读图缺陷：失败牌、通关 CTA、第二世情报条、南侧逃逸口、仓道黄区、电台/油库相似度。
- 六夜地标、地面材质和环境光形成区别；不改变通行几何来解决纯视觉问题。
- 行走、转向、射击、命中、死亡、拾取、开匣、警报、通关的反馈完整；动画不负责结算伤害或推迟真实状态。
- 处理暂停、倍速、切关时的 Tween/特效生命周期；设置中提供必要的减弱动态/闪烁选项。
- Look 改动沿用 PaperRoute：生成脚本 → GLB 与 clay/shaded 多视图 → 烘焙 2D 资源 → 独立接入 → 游戏帧复核。缺陷需指出具体画面位置。

### M3-03 声音和叙事收尾

- 使用手机扬声器与耳机试听选择、开匣、敌我开火、空弹、拾取、漏网、回波、胜败、分夜底音。
- 检查并发限流、峰值、掩蔽、静音、音量滑块和后台恢复。PCM 指标是技术检查，听感需实际试听。
- 六夜环境底音建立场所区别；警报、危险、拾取有稳定含义，不能让 UI 音抢过关键信号。
- 简报只保留任务情境、关键目标与当前战术提示；详细按键说明放在可重看的帮助里。
- 通关、致谢与战役档案完整；清理开发占位文字与过期版本号。
- 建立实际使用资源的来源和许可台账；未接入的素材不算完成资产。

M3 退出：六夜均通过玩法、读图与耳听复核；完成新目录下至少 31 张战役流程图，以及触控/取消/重试等必要增补帧；全战役试玩完成并闭环阻塞问题。已有 eval 目录不覆盖。

## 8. M4：安卓稳定性与数据封板

### M4-01 设备矩阵

M0 尽早选定可获得的具体机型；Beta 至少覆盖：

- 一台预期性能下限的 arm64 安卓手机。
- 一台常用中端手机。
- 两种以上横屏宽高比，至少包含全面屏/系统手势区域；必要时补一台设备或模拟器覆盖系统版本。
- 桌面 Compatibility/强制触控与模拟器用于辅助定位，分别记录，不能算作真机结论。

候选包用同一源码 SHA、版本号与 APK 哈希。记录机型、系统、渲染器、画质档、测试时长和环境。

### M4-02 可靠性回归

- 安装、首次启动、拒绝无关权限、离线六夜通关、标题返回和继续进度。
- 短按/长按/拖拽/多指/取消/边缘手势；UI 点击不穿透到战场；所有必需动词可触达。
- 刘海/系统栏/横屏方向/暂停覆盖层变化后，点击区与视觉坐标一致。
- 返回键按层关闭，切后台停止模拟与音频，恢复时仍暂停并等待玩家确认。
- 对安全边界进行进程终止、存储失败、损坏文件、未知 schema、旧版迁移和多次重启测试。
- 重玩旧关不丢最高解锁，不把一关的情报恢复到另一关。
- 在每种实际发布签名关系上验证覆盖安装；旧 debug 包与新 release 包签名不同的情况单列。

### M4-03 性能与质量目标

以下为计划验收目标，M0 实测后冻结具体机型和指标口径：

- 中端标准档目标 60fps，低端省电档目标稳定 30fps；用帧时间记录分析，不只看瞬时 FPS。
- 每台目标机最复杂场景连续运行至少 30 分钟，无崩溃、ANR、音频失控或使操作失效的长时间卡顿。
- 在约定采样区间内，帧时间第 95 百分位目标分别不高于约 20ms / 40ms；未达到时检查瓶颈，或明确收窄支持机型，不直接勾选通过。
- 连续切关/重试 20 次后，内存与节点数量回到稳定区间，无持续增长；记录基线与后测值。
- 保持存档、触控和核心规则正确性，不通过牺牲命中准确、碰撞或模拟一致性换取性能指标。

### M4-04 可维护的回归入口

- 建立统一的环境检查、隔离导入、主冒烟、关键交互与 APK 构建入口。
- 自动化先覆盖本次真正改变的行为，再运行必须的全量回归；不为每个内部字段写镜像测试。
- 对应 PR 附上日志、版本、SHA 和截图；提供可在干净工作副本复现的命令。
- CI 固定引擎与模板、超时和日志归档；签名凭据留在受控存储中。
- 对 main.gd 的重构仅限已证明妨碍修复/验证的部分。保留全套行为基准，不把全面架构改写塞进封板。

M4 退出：功能冻结；核心阻断缺陷清零；两类目标设备通过；存档/升级矩阵完成；能够从干净源码构建同一候选版本。

## 9. M5：RC、正式包与维护交接

### M5-01 候选版验收

- 冻结一个候选 SHA，重新构建 APK；检查所有证据是否对应此版本。
- 从新档走完整六夜，再从上一受支持版本做升级/继续；标题、简报、失败、重试、通关、致谢、档案全部覆盖。
- 影响核心规则、存档或输入的最后修复必须重跑受影响路径及规定的全量门槛；证据引用不能沿用修复前 SHA。
- 一名未参与当前实现的审阅者检查证据与未解决项；无独立审阅时如实标注，不伪造 approve。

### M5-02 签名与旧包迁移

固定包名与发布签名身份，正式密钥由所有者保管、备份，构建只读取凭据。安装/升级需要符合 Android 的签名规则，见 [Android 官方应用签名说明](https://developer.android.com/studio/publish/app-signing)。

M0 调查旧 v0.6.11 与现存用户包的证书；M4 做真实升级验证。若旧 debug 签名无法沿用，不能承诺原地覆盖升级，也不能把“卸载重装”作为保档方案；需交付已测试的导出/导入迁移，或明确旧试玩数据不可迁移的边界并在发行决策前解决。1.0 之后的补丁保持签名兼容与单调增加的 versionCode。

### M5-03 发布包与源码整合

交付目录包含：

- 正式签名 APK、SHA-256、包名/版本/签名证书指纹。
- 安装、横屏操作、继续游戏、升级与数据恢复说明。
- 版本变更、已知问题、设备覆盖、实际资源致谢与许可。
- 构建清单：源码 SHA、引擎/模板/SDK、构建命令、验证记录。
- 真实游戏截图和 30–60 秒实际触控录像；展示的是交付 APK 的能力。
- 支持/反馈入口和问题报告模板；没有的信息不杜撰。

达成门槛后，基于届时最新 main 检查游戏分支依赖链（含 #61/#63/#64 的上游），形成范围清晰的集成 PR。先验证整合后游戏文件及非游戏路径，保留其它项目的近期变动，再合入默认分支并打正式标签；不能根据旧路线图假设 main 仍是空壳。

本轮只交付计划，不执行上述远端合并、签名、标签或发布。后续实施时在用户授权范围内完成发行动作。

### M5-04 1.0 后的短期维护

预留发布后 1–2 周维护窗口：处理安装、崩溃、存档与阻断缺陷，按实际问题出 1.0.x。保持旧包、源码和数据迁移说明可追溯。

恢复方案要考虑 Android 版本与存档兼容：优先停止分发问题包，并以更高 versionCode 发布修复；旧二进制通常不能作为无条件直接覆盖的“回滚包”。用兼容性验证后的恢复手段处理数据，不要求玩家随意卸载。

此安排是开发规划，不创建自动监控或预约后续运行。
